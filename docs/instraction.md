# 14. リニューアルサイト設計（新サイト提案）

## 14-1. リニューアルの基本方針

現状診断では「サイトが消えている」わけではなく、**情報の粒度が薄い／検索エンジンに正しく内容が伝わっていない／写真が予約の意思決定を後押しできていない**ことが本質的な課題でした。したがって今回のリニューアルは「作り直す」というより「宿の魅力を正しく変換する」ことを目的とします。

| 目的 | 現状の課題（診断結果より） | リニューアルでの解決アプローチ |
|---|---|---|
| 宿泊予約数の向上 | 客室の広さ・眺望・写真が不足。キャンセルポリシー等の安心材料がない | 客室タイプ別ページ化＋比較表＋安心材料（ポリシー・FAQ・口コミ）をCV導線上に常設 |
| ブランドイメージ向上 | 汎用テンプレート感が強く、宿の魅力（自然・開放感・写真の美しさ）が伝わっていない | 高級路線ではなく「リーズナブルに洞爺湖を満喫できるモダンリゾート」として、自然・開放感・写真主体のデザイン言語を再定義（詳細は19章） |
| モバイルファースト対応 | viewportは対応済みだが、電話・予約ボタンの視認性が弱い | スマホ専用の固定CTAバー、タップ最適化された導線設計 |
| インバウンド対応強化 | 多言語は外部OTAへ丸投げ | 自社ドメイン内に英語を中心とした多言語ダイジェストページを構築 |
| SEO流入増加 | meta description/title が全ページ共通のプレースホルダー | ページ単位でのメタ情報設計、FAQ・周辺観光等のロングテール獲得ページを新設 |
| 情報の探しやすさ向上 | グローバルメニューに主要導線（アクセス・プラン）が欠落 | 情報設計（IA）をユーザーの意思決定順（客室→温泉→料理→プラン→予約）に再構成 |
| 運営担当者が更新しやすい構成 | 現状CMSの実態が不明（プレースホルダー放置＝更新体制の形骸化を示唆） | Headless CMSによる「お知らせ・プラン・写真」の担当者更新を前提に設計 |

## 14-2. サイト全体のコンセプト

**「洞爺湖の湖畔に、いちばん近い時間を過ごせる宿」**

- 部屋数（和室35・洋室4）という“数の情報”から、“湖側の部屋から見える景色”という“体験の情報”へ転換する
- 温泉・お料理・客室・周辺観光を「非日常のはじまり」から「チェックアウト後の観光」まで時系列でストーリー化し、宿泊者の一日の流れをイメージさせる
- 情報量が薄かったページ（求人・福利厚生・お客様の声）は、サイト内で明確な役割を持つ独立ページとして再設計する

# 19. デザインコンセプト

## 19-0. ポジショニングの再定義

前版では「上質な湖畔リゾート」という高級旅館寄りのトーンで設計しましたが、これは実際のグランドトーヤの立ち位置とズレています。グランドトーヤは、**一泊数万円クラスの高級旅館ではなく、「手頃な価格で洞爺湖の自然と温泉をしっかり満喫できるカジュアルリゾートホテル」**です。デザインもこのポジションに合わせ、「格式」ではなく「開放感」「気負わず行ける」「写真映え」「予約のしやすさ」を軸に再設計します。

| 軸 | 高級旅館路線（不採用） | グランドトーヤが目指す路線（採用） |
|---|---|---|
| キーワード | 静寂・格式・一見さんお断り感 | 自然・開放感・気軽さ・のびのび |
| 写真の主役 | 器や設え、和の間 | 湖面・空・光、家族やカップルが楽しむ表情 |
| 余白の使い方 | 「間」を見せるための余白 | コンテンツを見やすくするための機能的な余白 |
| 色 | 深く沈んだトーン | 明るく開けた空気感のあるトーン |
| フォント | 明朝体中心 | サンセリフ中心、読みやすさ最優先 |
| 予約への態度 | 予約導線を控えめに、格式を優先 | 予約導線を常に目立たせ、迷わせない |

## 19-1. デザインコンセプト
> * **参考サイト**：[松島一の坊（ichinobo.com/matsushima）](https://ichinobo.com/matsushima/) の配色・落ち着いたトーンを参考にする。
> * **配色**：紺（ネイビー）×生成り（クリーム）×真鍮（ゴールド、アクセント）を基調とした落ち着いた配色とする。以前案の明るい水色×ミント×オレンジのカジュアルな配色は不採用とし、「ホテル・温泉宿らしい上質さ」が伝わる配色に変更する。
> * **フォント**：見出しは明朝体系（Noto Serif JP 等）、本文はゴシック体系（Noto Sans JP 等）を基本とし、上質で落ち着いた印象を優先する。
> * **写真の方向性**：ストック写真・イラスト装飾ではなく、**自社の実写真を中心に構成**する。写真点数を多く使い、館内の雰囲気が伝わることを重視する。
> * **アニメーション方針**：装飾的なアニメーション（スクロール演出、湯けむり・シマー等の常時ループアニメーション、ホバー時の過剰な動き等）は**極力使用しない**。スムーズスクロール程度にとどめ、操作性・視認性を優先する。

## 19-2. ブランドイメージ

上質さより「開放感」「コストパフォーマンスの良さ」「家族・カップルどちらにも合う気軽さ」を重視。堅苦しい老舗旅館の作法ではなく、「洞爺湖に遊びに行くのが楽しみになる」明るいリゾートホテルとして表現します。

## 19-3. ターゲット層

* ファミリー層（子連れでの利用しやすさを重視する層）
* カップル・夫婦の近場〜1泊2日旅行層
* 「高級旅館ほどの予算はかけたくないが、温泉と景色はしっかり楽しみたい」コスパ重視層
* 有料オプション（カヌー・ゴルフ・乗馬等）を目当てにするアクティブ層
* インバウンドFIT（個人旅行者）、道内・道外からの近距離リピーター

## 19-8. アニメーション方針

* スクロール時の軽いフェードイン・スライドインのみを基本とし、表示速度を損なわない範囲に留める
* 派手な演出（パララックス多用、大型動画背景の常時再生等）は避け、モバイル回線でも軽快に閲覧できることを優先
* 温泉・客室の写真ギャラリーはシンプルなスワイプ／タップ切り替えとし、直感的な操作性を重視

## 19-9. トーン＆マナー（文章）

* 敬語は保ちつつ、堅苦しい旅館言葉ではなく「親しみやすく、わかりやすい」文体を採用（例：「ごゆっくりお過ごしくださいませ」ではなく「洞爺湖でのんびり過ごしませんか」に近いトーン）
* 「コスパの良さ」「気軽に行ける」といった実利的なメリットも隠さず打ち出す。高級路線を装った誇張表現は避け、実際の価格帯・体験に即した誠実な打ち出し方をする
* 料金・プラン情報は曖昧にせず、具体的な数字（円・㎡・分）を積極的に見せることで「わかりやすさ＝信頼」を作る

## 19-10. 参考にすべき方向性

高級和風旅館サイトではなく、**国内外のカジュアル〜ミッドレンジのリゾートホテル／グランピング施設／道の駅併設ホテルのような「自然・写真・わかりやすい予約導線」を軸にしたサイト**を参考にするのが適切です。「間」や「余白の美」を強調するデザインではなく、**明るい色使い・大きな写真・シンプルな導線**で「気軽に予約できる湖畔リゾート」という立ち位置を一貫して表現します。

# 20. 技術構成の提案

## 20-0. 結論：低コスト運用の方針について

ご認識の通りで問題ありません。ホテルサイトのように「常時起動しているサーバーで処理をし続ける必要がない（会員機能・複雑な検索処理を自前で持たない）」サイトは、**サーバー（EC2・Lightsail等）を24時間稼働させる必要は基本的にありません**。

さらに、月額利用料が発生するSaaS型CMS（microCMS等）も使わない方針とし、**Decap CMS（旧Netlify CMS）というオープンソース（無料）のCMSをGitHubと組み合わせて使う構成**に変更します。

* **Astro（SSG）**＝ビルド時にページをすべて**HTMLファイルとして書き出す**方式。サーバー上でプログラムを常時動かして都度ページを生成する必要がない
* **Decap CMS**＝オープンソースの管理画面。コンテンツ（お知らせ・プラン・写真の情報等）はSaaSのDBではなく**GitHubリポジトリ内のファイル（Markdown/JSON）として保存**される。ソフトウェア自体の利用料は0円
* **S3＋CloudFront**＝生成されたHTMLファイル一式を置いておくだけの「静的ファイル置き場＋配信網」。OSのアップデートやミドルウェアの保守が不要
* **DB**＝コンテンツがGit管理下のファイルになるため、そもそもDBという概念自体が存在しない。予約機能は「手間いらず」「ねっぱん!」等の外部予約エンジン（SaaS）に埋め込み／リンクするのが業界標準で、これも自社でDBを持たずに済む
つまり「サーバーを持たず、月額課金のSaaSにも極力頼らない」というご要望に対して、**Astro＋Decap CMS＋GitHub＋S3/CloudFront**という構成が最も合致します。

## フロントエンド
**推奨：Astro**

| 選択肢 | 評価 | 理由 |
|---|---|---|
| Astro | ◎ 推奨 | ホテルサイトはインタラクション（予約フォーム等）が一部に限られ、大半が静的コンテンツのため、必要な箇所だけJSを読み込む「アイランドアーキテクチャ」が最適。表示速度・Core Web Vitals改善に直結し、現状課題の「多数のJS/CSSライブラリの一括読み込み」を根本解消できる。**ビルド後は純粋なHTML/CSS/JSファイル群になるため、サーバーを持たずS3のような静的ホスティングにそのまま置ける**。Decap CMSとの組み合わせ実績も豊富 |
| Next.js | ○ 次点 | 会員機能等を将来的に強化する前提であれば有力だが、サーバーサイド機能を使う場合は常時起動のサーバーやサーバーレス関数が必要になり、Astroの完全静的構成よりコストが上がる場合がある |
| SvelteKit | △ | 技術的には優秀だが国内制作会社・エンジニアの供給が少なく、長期保守の観点でリスクがやや高い |

**結論**：低コスト運用を最優先するなら、Phase 1〜3を通してAstroによる完全静的（SSG）構成を維持する。

## CMS
**推奨：Decap CMS（オープンソース・無料）＋GitHub**

| 選択肢 | 評価 | 理由 |
|---|---|---|
| **Decap CMS** | ◎ 推奨 | オープンソースでソフトウェア利用料は0円。コンテンツはGitHub上のファイルとして保存されるため、SaaS事業者への継続課金・将来の値上げ・サービス終了リスクがない。管理画面のフィールド構成（お知らせ・プラン・写真等）も自由にカスタマイズ可能 |
| microCMS等のSaaS型ヘッドレスCMS | △ 今回は不採用 | 管理画面の作り込みや画像最適化など機能面は充実しているが、月額利用料が継続的に発生する点がご要望と合わない |
| CMSなし（完全静的HTML） | ○ 更新頻度が極端に低い場合の代替案 | ソフトウェア費用ゼロという点ではDecap CMSと同じだが、更新のたびにHTMLを直接編集する必要があり、非エンジニアの担当者には負担が大きい |
| WordPress | × 非推奨 | 常時稼働のDB＋サーバーが前提となり、「サーバー・DBを持たない」方針と相反する |

### Decap CMSの仕組み（担当者向け操作画面について）

1. 担当者はブラウザで専用の管理画面URL（例：`grandtoya.com/admin/`）を開く
2. GitHubアカウントでログイン（ホテル用に発行した1〜数アカウントで運用）
3. 「お知らせ」「宿泊プラン」「写真」など、あらかじめ設計したフォーム項目に沿って入力・画像アップロード
4. 保存すると、裏側で自動的にGitHubへ変更内容がコミットされる
5. コミットをきっかけに**GitHub Actions（無料枠あり）**がAstroのビルドを実行し、生成されたHTMLをS3へ自動アップロード
この一連の流れに**常時稼働のサーバーは登場しません**。GitHub Actionsは「コミットされた瞬間だけ動いて数十秒〜数分で終わる」処理で、小規模サイトの更新頻度であれば無料枠（パブリックリポジトリなら無制限、プライベートでも月2,000分）に収まるのが通例です。

**ログイン認証について**：Decap CMSのGitHubログインには、OAuthのやり取りを仲介する小さな処理が1つだけ必要です。これは常時稼働のサーバーではなく、Cloudflare WorkersやAWS Lambdaのような「呼ばれた瞬間だけ動く」サーバーレス関数、またはNetlify／Vercelの無料プランに用意されている既製のOAuth連携機能で代用でき、実質無料で運用できます。

### 正直な注意点

* microCMSのような「至れり尽くせりの管理画面」に比べ、**Decap CMSは初期構築の手間がやや大きい**（フィールド定義、OAuth連携の設定、画像アップロード先の設定など）。ここは初回構築時に制作側でまとめて対応すべき部分
* サポート窓口がないため、トラブル時は制作会社・エンジニアに相談する前提で運用する
* 担当者はGitHubアカウントでのログインという操作に最初は慣れが必要（とはいえ、実際に触るのはDecap CMSのフォーム画面のみで、GitHubの複雑な操作を直接行うわけではない）
## インフラ（低コスト構成の詳細）
* **ホスティング**：ビルドしたHTML一式をS3に配置し、CloudFrontで配信。**EC2やLightsailのような「サーバー」は使用しない**
* **CI/CD**：GitHub Actions（無料枠内）でビルド・デプロイを自動化。常時稼働のビルドサーバーは不要
* **CDN**：CloudFront。AWSの無料利用枠（月1TBのデータ転送・1,000万リクエストが無料、2026年7月時点の公表内容。最新条件は要確認）の範囲内であれば、小規模な旅館サイトの通常アクセス量（月間数十GB程度）は配信費用がほぼ0円に収まる可能性が高い
* **ドメイン・DNS**：Route53を使う場合、ホストゾーン維持費が月$0.50程度。独自ドメイン自体の年間更新料（数百〜数千円）は別途必要
* **画像最適化**：Astroのビルド時画像処理（`astro:assets`）でWebP変換・リサイズを自動化し、追加のSaaS（Cloudinary等）に頼らない構成も可能。現状確認された2MB級jpgの問題を構築時点で構造的に解消
* **バックアップ**：コンテンツ自体がGitHubにコミット履歴として残るため、別途バックアップの仕組みを用意しなくても「いつでも過去の状態に戻せる」
## 参考：月額費用の目安比較

「サーバーを使う場合どれくらい費用がかかるか」の比較として、代表的な構成の目安を並べます（2026年7月時点の一般的な相場感。為替・キャンペーン・アクセス量により変動するため、契約前に必ず最新の公式料金をご確認ください）。

| 構成 | 月額費用の目安 | サーバー管理の要否 | 備考 |
|---|---|---|---|
| **①Astro＋Decap CMS＋GitHub＋S3／CloudFront（今回の推奨構成）** | ほぼ0円〜数百円程度 | 不要 | CMSソフトウェア自体は無料。かかるのは実質、独自ドメイン代とS3/CloudFrontのわずかな実費のみ。GitHub・GitHub Actionsも小規模サイトなら無料枠内で収まる |
| **②完全静的HTML＋S3／CloudFront（CMSなし）** | 数十円〜数百円程度 | 不要 | ①とほぼ同額だが、更新の都度HTMLを直接編集する必要があり、非エンジニア担当者には不向き |
| **③microCMS等のSaaS型CMS＋S3／CloudFront** | 数百円（無料プラン）〜約5,000円前後（有料プラン） | 不要 | 管理画面は使いやすいが、継続的な月額課金が発生するため今回は不採用 |
| **④AWS Lightsail（VPS）でWordPress運用** | 1インスタンスあたり約500円〜1,500円（$3.5〜$10/月）＋ドメイン代 | **必要**（OS・PHP・MySQL・WordPress本体・プラグインのアップデートやセキュリティ対応を自社／委託先で継続的に実施） | 一見安価に見えるが、保守作業を外部委託する場合は別途保守費用（月数千円〜）が発生するのが一般的 |
| **⑤国内レンタルサーバー（WordPress）でWordPress運用** | 990円〜1,320円程度（例：Xserverスタンダードプラン、契約期間により変動）＋ドメイン代 | **必要**（④と同様、プラグイン・本体のアップデート対応が継続的に必要） | 国内では最も採用例が多い構成だが、常時稼働のサーバー費＋保守の手間が発生し続ける |
| **⑥AWS EC2で自前構築** | インスタンス性能により月数千円〜数万円＋別途RDS（マネージドDB）を使う場合は追加で月数千円〜 | **必要** | 自由度は最も高いが、小規模なホテル1サイトの運用には過剰スペック・過剰コストになりやすく非推奨 |

**結論**：①（Astro＋Decap CMS＋GitHub＋S3/CloudFront）が、サーバーコスト・CMS利用料の両方を最小化しつつ、担当者による自走更新も維持できる最もバランスの良い構成です。「初期構築の手間はやや増えるが、ランニングコストは限りなくゼロに近づける」というトレードオフを許容できるのであれば、これを正式な採用方針とすることを推奨します。

## SEO・パフォーマンス
* **静的生成（SSG）を基本方針**とし、Decap CMSでの更新（＝GitHubへのコミット）をトリガーにGitHub Actionsが再ビルド・再デプロイ（サーバーの常時稼働は不要）
* Core Web Vitals対策：画像の遅延読み込み・次世代フォーマット化、不要なJS/CSSライブラリ（現状のjQuery/Owl Carousel/Fancybox等の重複読み込み）を廃し、必要最小限のコンポーネントのみ実装
* 構造化データ：LodgingBusiness、Room、FAQPage、BreadcrumbList、AggregateRating（口コミ）を各ページに適切に付与
* パンくず：全下層ページに実装しリンク化、構造化データも併設
* XMLサイトマップ：ビルド時に自動生成
* OGP：ページ単位で個別画像・タイトル・説明文を設定し、現状「og:title空欄」の問題を解消
